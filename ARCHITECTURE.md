# Exo Launcher architecture

Exo is a WinUI 3 host (.NET 11, Windows App SDK 2) with one WebView2 running React 19 (`ui/`). `ExoLauncher/MainWindow.xaml.cs` creates the host; `ui/src/components/LauncherApp.tsx` places every room through `Room` (`ui/src/components/shell/BootGate.tsx`). Behind the splash each room is warmed and laid out out of sight (`is-backstage` in `ui/src/exo-shell.css`: fixed at its own size under the Bar, hidden, inert, strictly contained), so a first visit costs what a later one does; reads stay tied to the room on screen.

The frontend uses its own controls (`ui/src/components/ui/`: `Button`, `Menu`, `Slider`, `Qr`; `ui/src/components/Switch.tsx`), Tabler icons through `ui/src/brand/icons.tsx` (DESIGN.md › Icons) and Tailwind 4. Styles are one file per room or surface in `ui/src/styles/`, imported in order by `ui/src/tokens.css`, then `ui/src/exo-shell.css`, `styles/rooms.css` and `styles/hosted-room.css` from `main.tsx`. The three Appearances are `<html data-exo-theme>` (DESIGN.md › Tokens).

React calls typed methods in `ui/src/lib/host.ts`; `Services/WebHostBridge*.cs` dispatches them to native services. Store adapters own official-client launch, ownership, installation and updates. Secrets stay in native stores.

- WebView2 (`Helpers/WebViewEnvironmentFactory`, user-data folder `webview`, `webview-debug` in Debug): the shell and the music web players share one environment, so one browser, GPU and network process; GOG and Epic sign-in (`Services/StoreAuthWindow`) make short-lived environments of their own. The shell runs on the Default profile at `app.exo-launcher.local` with web messages and no host objects, plus its own `*.exo-launcher.local` hosts (covers, thumbnails, Exo Mouse, payments, captures). The YouTube Music and Apple Music players run on the named `embedded` profile with none of those, and its extensions (uBlock Origin Lite, SponsorBlock, Better Lyrics; `Helpers/WebExtensions`, each pinned to the hash of its folder) live only there. Never give an embedded view a host object or virtual host, and never attach an extension to the shell.
- Start (`MainWindow.PrepareConnectedRoomsAsync`, `shell.prepare`, once the library is usable and onboarding is done, again on every shell load and provider switch): Exo's Discord session connects, Exo Capture and Exo Shaders' engine start, and the chosen music service's engine starts hidden (the YouTube Music or Apple Music page, or the installed Spotify app; a Spotify already running is adopted hidden). An idle music player sleeps (Spotify freezes, a web player suspends), then closes after 15 minutes asleep (`MusicReleaseDelay`: the web view, or a desktop app Exo started, never one the user had open). Steam is never started to check ownership (`Adapters/SteamClientReady`). `tools/measure-memory.ps1` prints the process tree's memory; the design target is one process per Chromium role.
- Background behavior (`MainWindow.TrimLoopAsync`, `Helpers/BackgroundTrim`, `Helpers/ForegroundWatcher`, `Helpers/ManagedProcessResources`): "in front" means the foreground window belongs to Exo's process, or to a hosted client while Exo owns its window (an `EVENT_SYSTEM_FOREGROUND` hook compares the foreground window's root owner with Exo's; `Window.Activated` is unreliable with a foreign top-level HWND). Managed scope is explicit: one cohort per root (Exo, Exo's WebView2 environment, Spotify's tree while selected, and each store client's UI helpers), walked with start-time checks so a reused parent pid never pulls in an unrelated process or Exo itself. The loop ticks every 5 s while Exo is behind, a hidden embedded renderer exists or a change is settling (15 s), and every 30 s otherwise.
  - While Exo is not in front, managed processes get low memory priority (not a playing Spotify, nor Exo's host during a call), the host enters efficiency mode, and Spotify drops to BelowNormal unless it is playing. Hidden embedded renderers (and a hidden, playing Spotify's UI renderer: Spotify plays from its host process) have their working set emptied, again only after 32 MB of growth (`ManagedProcessPolicyState.RetrimGrowthBytes`) and at most every 30 s. Exo's own host and shell lose their working set only while its window is minimized or hidden.
  - A hosted client whose room is closed gets EcoQoS (`HostedProcessClass.ShouldThrottle`) on the processes that only draw or store for it, never audio, network or DRM; opening the room clears it at once. Spotify freezes after 30 s idle (`HostedProcessClass.IdleFreezeDelay`), a hidden web player suspends after 60 s silent; music is never suspended while playing.
  - A client window hidden before it ever reached the screen keeps drawing while hidden, so `DesktopClientHost.PrimeHidden` shows it once for a second through a one-pixel region over Exo's client area; cross-process `DWMWA_CLOAK` is refused by Windows, and an empty-region or off-screen show does not count as visible to Chromium.
  - Store clients' UI helpers (`Adapters/StoreClientHelpers`: steamwebhelper, EpicWebHelper or WebView2 under EpicGamesLauncher, QtWebEngineProcess under EADesktop, UplayWebCore under upc or UbisoftConnect, GalaxyClient Helper, Battle.net's `--type=` renderers; each a start-time-checked child chain of the client's root, so nothing a game started can join): while the client has no main window on screen, is not in an Exo handoff and was not just opened by the user or a sign-in, they get low memory priority and an emptied working set (after 32 MB of growth, at most every 5 minutes, since the Steam overlay draws in steamwebhelper). No EcoQoS or priority class, nothing closed or suspended, never the client's main process or services, and Riot is not in the list.
  - Nothing on screen is trimmed, no process outside the cohorts is touched, and everything is restored on return. `MainWindow.Resources` sums the cohorts for a `Trim:` line in app.log every 5 minutes.
- Discord is Exo's own client (`Services/DiscordClient`, `discord.*`; `docs/architecture/discord-client.md`): the host holds the session, REST, gateway and voice, and the page draws the room. Its unread count reaches the Bar's tab and the taskbar button through `friends.badge`. Exo never hosts, installs or patches the Discord desktop app (it can uninstall it, `Services/ReplacedApps`).
- Hosted apps are always optimized; there is no setting, and an older Exo's `appOptimizations` and `discordEquicord` keys in `settings.json` are ignored. It is applied on every start through Exo, so an app update that replaced its files is optimized again; an app running outside Exo is left alone. Spotify: `Helpers/SpotifyAmoledTheme` appends one marked block to the xpui stylesheet (verified against a recorded stock backup; an xpui it does not recognize is left stock) and writes Spotify's own prefs (`ui.hide_hpto`, `ui.hide_promoted_songs`, no OS track notifications, no hardware acceleration); `Helpers/SpotifyControls` adds a Canvas pause to its DevTools script. YouTube Music and Apple Music: `Helpers/EmbeddedClientPresentation` marks the page, hides upsells and skips a hidden page's layout and paint (`content-visibility`).
- Music is Exo's own player for Spotify, YouTube Music and Apple Music (`ui/src/components/music/`: `NativeMusicRoom` runs the engine's lifecycle, `MusicPlayer` draws library, home, search, pages, panels and the player strip; `docs/architecture/music-engines.md`). Each service plugs in through an adapter in `ui/src/lib/musicAdapters.ts` answering the same shapes (`ui/src/lib/player.ts`); Jam, Friend activity and Devices show only for a service that has them. The service runs hidden as the engine; Exo never reads a token, plays or decodes audio, or changes what the account may do.
  - Spotify (`spotify.start` / `view` / `act` / `leave` / `link` / `signIn`, `MainWindow.SpotifyRoom`): the desktop app, installed on consent (its signed installer) and started hidden by `DesktopClientHost`, which holds it as an owned popup (ownership, not SetParent: a reparented Chromium window loses activation and keyboard input). It is never placed on screen; only a missing install falls back to the hosted `MusicRoom`, and sign-in goes through the default browser. While the room is open `SetEngineWanted` keeps the tree from the idle freeze. `Helpers/SpotifyNative` installs one adapter in xpui over the loopback DevTools session (`Helpers/SpotifyPage`): Spotify 1.3's platform APIs are a registry keyed by `Symbol.for(name)` (PlayerAPI, LibraryAPI, PlaylistAPI, ShowAPI, ConnectAPI, ConnectDevicesAPI, SocialConnectAPI for Jam, BuddyFeedAPI for Friend activity, RecentlyPlayedAPI, RequestBuilder), found through the React tree; catalog pages go through the client's own GraphQL with this build's persisted-query hashes (`Helpers/SpotifyQueries` reads them from the installed xpui.spa and caches them until it changes), lyrics through RequestBuilder to color-lyrics. Answers are shaped in the page into small DTOs; the host only validates URIs and ids. A Jam's join token stays in the page; only its share link leaves it.
  - YouTube Music (`ytmusic.start` / `view` / `act`, `MainWindow.WebMusicRoom`): music.youtube.com loads hidden (transparent, no input) and `Helpers/YouTubeMusicNative` evaluates in it through WebView2's DevTools protocol: pages from its own InnerTube client (/browse, /search, /next, /like), playing and skipping through its `yt-navigate` event, shuffle and repeat through its player bar, queue and like state from its store. Ids cross as `ytm:<kind>:<id>`.
  - Apple Music (`applemusic.start` / `view` / `act`, the same `WebMusicRoom`): its Windows app is native WinUI/C++ with nothing to drive without UI automation, so the engine is music.apple.com (opened on its search page), driven by `Helpers/AppleMusicNative` through the page's own `MusicKit.getInstance()`: Home, recently played, catalog, library, lyrics, favorites and playlist edits through the same `api.music` calls the page's menus send, with its developer token and the user's sign-in, which Exo never reads; play and transport run as the user's click (`userGesture`). Playback and its DRM stay inside Apple's page. Ids cross as `am:<type>:<id>`. A saved Cider choice reads as Apple Music (`WebClientPreferences`).
  - Switching providers retires the previous session off the UI thread (`DesktopClientHost.Retire`: polite close, bounded wait, terminate) and the replacement waits for that tree to be gone, because the clients are single-instance. Leaving Music for another room only hides it.
  - The mini player: `Services/MediaSessionService` reads the song from the provider's page (`MusicNowPlaying`), Spotify from its Windows media session (SMTC) while its page can't answer, and sends transport to the same source. Volume is the app's own (`Services/MusicAppVolume`: Spotify's PlaybackAPI, YouTube Music's player element, Apple Music's `MusicKit.getInstance().volume`), long-polled into `music.volume`; the first answer folds the Windows session volume into it. A provider with no page to ask falls back to `Services/AppVolume`, its WASAPI session volume, re-read every second while shown (5 s while Exo is behind).
- Devices is Exo Mouse, a separate program in `mouse/` (AGPL-3.0-or-later, `mouse/LICENSE`) built on `@openmouse/protocol` (AGPL-3.0, pinned 0.45.2). Exo Launcher is not covered by the AGPL; the two meet only through postMessage. The `ui` build runs `npm --prefix ../mouse run build` into `ExoLauncher/wwwroot/mouse`, and `DevicesRoom.tsx` frames it on its own origin, `https://mouse.exo-launcher.local` (`.exo-devices-frame`), filling the room.
  - The relay (`ui/src/lib/mouseRelay.ts`, installed once with Exo and never removed, so the module works while the room is hidden) answers only `hid.list`, `hid.open`, `hid.close`, `hid.sendReport`, `hid.sendFeatureReport`, `hid.receiveFeatureReport`, `hid.receiveInputReport`, `exo.games` (installed games by id, title and cached cover thumbnail, for game-linked profiles), `exo.profiles.read` / `write` (`mouse.profiles.get` / `set`, `mouse\profiles.json` under Exo's data folder, at most 512 KB), `exo.textScale`, `exo.motion` and `exo.theme`. It takes one-way notices, battery state (Exo status lines and the Bar's mouse capsule) and the active profile's name, and posts only `hid.input`, `hid.changed`, `game.runState` (id, `isRunning`), `exo.textScale`, `exo.motion` and `exo.theme`; `DevicesRoom.tsx` posts `room.visible`. Messages from anywhere but that frame, and every other method, are ignored.
  - Native HID is `Services/Hid/HidService` (+ `HidInterop`) behind `WebHostBridge.Hid`: devices listed as WebHID does (collections grouped by their USB interface, so two identical mice stay separate), every collection opened shared, never exclusive (which would freeze the mouse's own input); of the collections Windows keeps, keyboards are skipped and a mouse collection is opened with no access, for feature reports only. Input reports are read from open, Chromium's byte conventions matched, a blocked control transfer abandoned after 3 s, arrivals and removals announced through `CM_Register_Notification`. Devices are named by an opaque hashed key; no device path reaches the page. No vendor software, bridge or driver install.
  - `mouse/scripts/patch-protocol.mjs` runs before each build and stops it when the library version changes. It teaches the library the Finalmouse Starlight X (the receiver light's TMR-DS mode 4 and custom color, command 54; command 53 actuation; the cabled 361d:0310/0311; battery 255 on command 38).
  - `Services/MouseBridgeRetirement` runs once for users of the retired OpenMouse Bridge mode (`settings.json` `mouseBridge: "exo"`): Exo's `openmouse-bridge.json` profiles go into the app's `config.json` (never while it runs), then the settings are cleared. The app is not started and its sign-in entry is not put back.
- Store (`Services/StoreService*.cs`, `store.*`) reads only public, anonymous storefront endpoints and caches each answer under `store`. Home: Steam's IStoreQueryService/Query (top sellers, coming soon, on sale with `price_filters.min_discount_percent`), the most-wishlisted list and Epic's free games, saved as `home-v5.json`. Card facts come from IStoreBrowseService/GetItems in batches of 50 into `items-v2.json` (fresh 12 hours, kept two weeks); tag names from IStoreService/GetTagList into `tags-v1.json` for a week. `store.game` answers from appdetails (4 s, then one 8 s retry) plus GetItems (3 s cap), deduplicates concurrent asks (hover warm-up, then click) and caches 20 minutes; `store.gameOffers` adds CheapShark's official-store rows (3 s). Epic's GraphQL is not used: it sits behind Cloudflare bot protection, and Exo does not work around that. PC requirements are read out of Steam's HTML (`StoreService.Specs.cs`) and judged against this PC at answer time (`StoreService.Fit.cs`, `Helpers/SystemSpecs.cs`: processor, graphics card, memory and Windows read once, free space on the roomiest Steam library drive each time), each part on one rough performance scale per kind, compared with the same maker's part when the game names one. Search caches 5 minutes per query and a newer query cancels the one in flight. `store.changed` carries `what` (`home` or `wishlist`) so the room reloads only that part. PERF lines in app.log time each source.
- Covers: `Services/CoverArtService` caches art under `covers\`, which the shell reads at `covers.exo-launcher.local` (no UI-thread work). Small art (grid cards, folders, captures, Shaders, Upscalers, Exo Mouse's games) asks `thumbs.exo-launcher.local/<cover file>?w=<px>` (`ui/src/lib/coverThumb.ts`): `MainWindow.ThumbnailResourceRequested` defers to `CoverArtService.ReadThumbnailAsync` (`CoverArtService.Thumbnails.cs`), which decodes the JPEG with Windows.Graphics.Imaging (EXIF-oriented, sRGB), scales it with its own Lanczos-3 pass (Fant first only above 4096×4096), stores `thumb-<w>-<stamp>-<cover>.jpg` beside it (stamp: a hash of the source's length, write time and the thumbnail format, so a replaced cover gets a new thumbnail and the old one is deleted), and serves the original when it is PNG/GIF/WebP or the thumbnail would be within a quarter of it. `w` is twice the widest card the screen can produce in device pixels, in 120 px steps from 240; it only grows within a session, and above 720 the original is used. The game sheet's cover loads the full file and shows the card's bitmap until it decodes.
- Achievements are read natively per store (`Services/AchievementService`) after a launched game exits and when a game's sheet opens with missing or stale counts. Steam reads `librarycache/achievement_progress.json` and the per-game librarycache file, and the Web API alongside when a key is stored. The counts stay on this PC; the sheet shows them (`game.extras`, `game.achievements`). There are no unlock pop-ups.
- Shaders: System › Shaders is Exo Shaders, Exo's own shader add-on (a GPL fork of SCSKiller 1.3.0, source at github.com/ImAvgErix/exo-shaders): a headless engine (`Services/ShadersAddon`, NDJSON over stdio) driven by Exo's own page (`ui/src/components/shaders/ShadersBoard.tsx`, `shaders.addon` / `shaders.call`, `MainWindow.Shaders`). Without the add-on the tab says Exo Shaders is not installed. `Services/ScsKillerStatus` answers `shaders.estimates` (each game's compile time on this PC) and `shaders.status` for a game sheet from the engine's `games.json` and each game's `games\<id>\state.json` (Warmed only for a `WarmedDriverId` whose driver is installed now), watches both to post `shaders.changed`, and once deletes the `tools\scskiller` copy older versions downloaded.
- Upscalers: `Services/DlssSwapService` finds DLSS / FSR 3.1 / XeSS files in a game, swaps them with backups (the first-shipped `.dlsss` and `.exo-bak`, with `.exo-written` and `.exo-stale` markers and a `.exo-upscale.json` sidecar) and restores them byte for byte. Releases are the compiled-in pins (SHA-256), each vendor's newer GitHub releases (`DlssSwapService.VendorWatch`: at most hourly, NVIDIA DLSS, AMD's FSR SDK and Intel XeSS are asked for their latest; a newer one's DLLs that a scanned game ships are fetched from its commit, checked against GitHub's size and blob hash and the vendor's signature, and kept in `dlss\vendor-releases.json`) plus DLSS Swapper's public manifest (`DlssSwapService.Catalog`, at most daily into `dlss\catalog-v2.json`; dev, unsigned and DLSS 1 builds dropped). FSR 3.1 builds are compared by their release (1.0.2.38022 is 3.1.2), not their loader's version. A catalog file is used only after its first download matches the manifest's size and MD5 and passes the vendor signature, export and exact-version checks; its SHA-256 then goes into `catalog-trusted.json` and is checked like a pin. Downloads come only from the pinned GitHub URLs and `dlss-swapper-downloads.beeradmoore.com/<kind>/`. DLSS's three files and FSR 3.1's two share one release id, so an update sets its siblings to the same release. Exo only moves a file to the newest release (the UI offers no older one); Update all (`dlss.updateAll`) is the only bulk path. DLSS presets are part of the GPU profile. NVIDIA's NGX overlay (`NGXCore\ShowDlssIndicator`, HKLM) is changed only through an elevated `reg.exe`, so Windows prompts each time.
- Capture: Exo Capture (`capture/`, C++, GPL-3.0-or-later, `capture\build.ps1`) is a separate program, shipped under `addons\capture` (or `%LOCALAPPDATA%\ExoLauncher\addons\capture`, which wins), started at `shell.prepare` by `Services/CaptureAddon` and spoken to in NDJSON over stdio (`MainWindow.Capture`, `capture.*`, events `capture.state` / `capture.saved`). It captures the running game's window (found by its process image under the game's install folder) or the screen with Windows.Graphics.Capture at the clip's rate (60, or up to 120 fps), at the lowest GPU priority. When Windows capture gets no frame from a game window for five seconds (exclusive full screen), it takes frames from inside the game with OBS Studio's own signed graphics hook (`capture\third_party\obs`, OBS's anti-cheat-compatible injection; `capture/src/hook.cpp` speaks OBS's hook protocol). Never for Riot games, while FACEIT or ESEA runs, for Store apps, or when another app already captures that game. It converts on the GPU (D3D11 video processor, BGRA to NV12/P010) and encodes with the GPU's Media Foundation encoder (NVENC, AMF, Quick Sync on the capturing adapter; AV1, else HEVC, else H.264, only a codec Windows can play back, stepping down when an encoder refuses to start), so frames never touch the CPU. Sound is four AAC tracks: the mix, the game (process loopback of its tree; on the desktop everything but Discord), Discord, and the default microphone; a missing source is a silent track. Instant replay keeps encoded packets in RAM from a key frame (one a second); a recording writes MP4 plus a packet journal (`.exo-rec`) that rebuilds a file cut short. Trim is a key-frame cut without re-encoding; Discord and Vertical exports re-encode to H.264. Snips are taken by the add-on, copied at once, saved as PNG and opened in the Captures sheet's editor; on an HDR screen the frozen picture comes from desktop duplication in FP16 scRGB, tone-mapped to sRGB against Windows' SDR white. The shell reads captures from `captures.exo-launcher.local` and `capture-thumbs.exo-launcher.local`. Without the add-on the Capture button hides and Settings › Capture says Exo Capture is not installed.
- Exo has no account or server of its own. `Services/LegacyProfileDataCleanup` runs once per start (deferred, after the shell paints) and deletes, by exact name in `%LOCALAPPDATA%\ExoLauncher` and `%APPDATA%\ExoLauncher`, what retired features left behind (for the retired Exo account, `auth.bin` (+ `.tmp`) and `online-cache`). It never contacts a service.
- GPU profile (`Services/GpuProfileService`, `gpu.profile` / `gpu.import`, System › Graphics › Driver and profile): one NVIDIA global profile per GeForce series (GTX 10/16, RTX 20/30/40/50) in two variants, G-SYNC or No G-SYNC (preselected from the main screen's variable refresh, `Helpers/NvidiaProfiles.Vrr`). `Helpers/GpuProfile` holds every value (pure, tested); `docs/architecture/gpu-profiles.md` has each setting's verdict, reason and source. G-SYNC: on for full screen only, driver V-Sync on, NVIDIA Reflex's cap (refresh × 3600 / (refresh + 3600), never closer than 3 under the refresh); No G-SYNC: variable refresh off, V-Sync and caps the games'. Both: Low latency On, a shader cache that never shrinks, DLSS presets (Super Resolution K and Ray Reconstruction F on RTX 20/30, NVIDIA's recommended on RTX 40/50, Frame Generation C on every RTX card), and NVIDIA's defaults back for placebo or harmful tweaks. Use Exo's profile writes every setting of the variant the driver lists to the global profile in one session, after saving every value it replaces to `gpu-profile.json`; Undo writes those back and a re-apply or variant switch keeps the first backup. Each read compares the driver with the applied variant, so a value moved by a driver update or another tool shows Re-apply. A Profile Inspector .nip (`Helpers/NvidiaProfileImport`) of the global profile is read into a plain-words preview and applied; Undo puts back what it replaced (kept until Exo closes). A Radeon gets its own profile (`Helpers/GpuProfile.Radeon`, written by `Services/RadeonProfileService` through ADLX's official Set calls in `Helpers/AmdAdlx.Settings`, backed up to `amd-profile.json` first, Undo the same); Anti-Lag in its default "while you play" and Fluid Motion Frames per game (`gpu.game`, `amd-games.json`) switch on in `LaunchOrchestrator.GameLaunching` and back once no game runs; `gpu.sensors` reads its temperature, power, clock, VRAM and fan. When ADLX does not answer, and on Intel (`Helpers/IntelIgcl`), the page lists what to set by hand next to what the driver holds.
- Settings is one sheet with a section list: General, Downloads, Music, Lucid, Capture, Game stores, Clean up, Optional keys, About (`ui/src/components/SettingsPanel.tsx`). Discord's settings are its own, in the Discord room.
- One layout on every screen: `MainWindow.PageScale` lays the page out as on a 1080p screen and draws it larger on a bigger one (`EXO_PAGE_SCREEN` tries another screen's zoom).

`MainWindow` is the only window XAML (`App.xaml` and the `Styles/` dictionaries aside); sign-in and connected-app windows are built in code. `ExoLauncher/Ui/` holds two small host helpers (`CaptionDragRegions`, `ExoUrlLaunch`), not a second room system. Do not rebuild native rooms when changing the React UI.

`hostMock.ts` loads only during development and tests. Protocol v1 method names and update-result types are checked against native source by `npm run contracts`; intentional changes regenerate `ui/contracts/host-v1.json` and `hostWire.ts` with `npm run contracts:write`. `npm run dead` runs knip in default and production mode (`knip.production.json`), so a file or export reachable only from tests fails the gate. `npm run css:prune` reports stylesheet blocks whose classes no component uses. `tools/find-dead-types.ps1` lists host types with no references outside their declaration. Cache lifetimes are in [docs/CACHE_POLICY.md](docs/CACHE_POLICY.md).

`npm run build` in `ui` emits into `ExoLauncher/wwwroot`; the project build runs it (`ui/scripts/build-cache.mjs`, only when its inputs or outputs changed) before collecting web assets. The shipped app runs from `%LOCALAPPDATA%\ExoLauncher\app`. Validate in the installed app after deployment.
