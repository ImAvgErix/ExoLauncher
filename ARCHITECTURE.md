# Exo Launcher architecture

Exo is a Windows launcher with a WinUI 3 host and one WebView2 running React 19. The current project targets .NET 11 and Windows App SDK. `ExoLauncher/MainWindow.xaml.cs` creates the host; `ui/src/components/LauncherApp.tsx` owns the visible rooms.

The frontend uses native controls (`ui/src/components/ui/Button.tsx`, `Switch.tsx`, the popover `Menu` in `LibraryShelf.tsx`), Exo's own icon set (`ui/src/brand/icons.tsx`, DESIGN.md › Icons), Tailwind 4, and a true-black AMOLED canvas. Room layouts live in `ui/src/styles/rooms.css`; existing library styles remain separate.

React calls typed methods in `ui/src/lib/host.ts`. `WebHostBridge.cs` dispatches these requests to native services. Store adapters remain responsible for official-client launch, ownership, installation and updates. Secrets remain in native stores.

- All WebView2 surfaces share one environment (`Helpers/WebViewEnvironmentFactory`, user-data folder `webview`) and therefore one browser, GPU and network process. The shell runs on the Default profile with host objects, web messages and the `exo` virtual host; the YouTube Music and Apple Music web players run on the named `embedded` profile with none of those, and one uBlock Origin instance covers that profile. Never give an embedded view a host object or virtual host, and never attach the ad blocker to the shell. `MainWindow.PrepareConnectedRoomsAsync` (`shell.prepare`, sent once the library is usable) starts nothing just to be ready: it only adopts, hidden, a Discord or desktop music app the user already runs. Discord and every music service start when their room opens; an idle music player is suspended or frozen, then closed after 15 minutes asleep (the web view, or a desktop app Exo started). Exo's own parts start with Exo, after the library: Exo Capture (its hotkeys), Exo Mouse's page (game-linked profiles, battery) and Exo Shaders' engine (its page opens at once; it sees every play session and queues driver-update rebuilds for idle time). Steam is never started to check ownership (`Adapters/SteamClientReady`). `tools/measure-memory.ps1` prints the process tree's memory; the design target is one process per Chromium role.
- Background behavior (`MainWindow.TrimLoopAsync`, `Helpers/BackgroundTrim`, `Helpers/ForegroundWatcher`): "in front" means the foreground window belongs to Exo's process — or to a hosted music-client tree while Exo owns its window (an `EVENT_SYSTEM_FOREGROUND` hook compares the foreground window's root owner with Exo's window; `Window.Activated` is unreliable with a foreign top-level HWND). Managed scope is explicit: `Helpers/ManagedProcessResources` builds one cohort per root — Exo itself, Exo's own WebView2 environment, and each hosted client's process tree plus approved same-directory auxiliaries (Spotify while selected). Windows still owns those vendor processes; Exo only manages them. The loop ticks every 5 s while Exo is backgrounded or just after a visibility change, and every 30 s otherwise. `BackgroundTrim.ApplyManaged` empties the working set of hidden embedded renderers (and of a hidden, playing Spotify's UI renderer, since Spotify plays from its host process), re-trimming only after 32 MB of growth. Process trees are walked with start-time checks, so a reused parent pid never pulls an unrelated process, or Exo itself, into a client's tree; while Exo is not in front every managed identity gets low memory priority, the host enters efficiency mode, and hosted clients drop to BelowNormal — except a client whose SMTC session reports Playing, which keeps Normal priority to avoid lowering playback scheduling priority. This does not guarantee glitch-free playback under all system loads. Exo's own host and shell processes lose their working set only while its window is minimized or hidden. A hosted client whose room is closed gets EcoQoS (`HostedProcessClass.ShouldThrottle`) on the processes that only draw or store for it: everything but audio, network and DRM while silent, and only the UI-only processes (Spotify's renderer, GPU, utility, crashpad) while a song is live; opening the room clears it at once. A client window hidden before it ever reached the screen keeps drawing while hidden (a prewarmed Chromium client animating its own UI), so `DesktopClientHost.PrimeHidden` shows it once for a second through a one-pixel region over Exo's black client area; cross-process `DWMWA_CLOAK` is refused by Windows, and an empty-region or off-screen show does not count as visible to Chromium. Everything is restored on return. `MainWindow.Resources` reports the cohorts' combined working set and private bytes to Settings, marked partial when membership or process access is incomplete. Store clients' UI helpers are a cohort too (`Adapters/StoreClientHelpers`): steamwebhelper under steam.exe, EpicWebHelper or WebView2 under EpicGamesLauncher, QtWebEngineProcess under EADesktop, UplayWebCore under upc, GalaxyClient Helper under GalaxyClient, and Battle.net's `--type=` renderers, each found as a start-time-checked child chain of the client's root so nothing a game started can join. While the client has no main window on screen, is not in an Exo handoff and was not just opened by the user or a sign-in, they get low memory priority and an emptied working set (again only after 32 MB of growth, at most every 5 minutes, because the Steam overlay draws in steamwebhelper); shown again, they return to normal memory priority. No EcoQoS or priority class, nothing is closed or suspended, the client's main process and services are never members, and Riot is not in the list. Nothing on screen is ever trimmed, and no process outside the managed cohorts is ever touched. Music is never suspended while playing; a paused hidden player suspends after 60 s.
- Friends is Exo's own Discord client (`Services/DiscordClient`, `discord.*`; see `docs/architecture/discord-client.md`): the host holds the session, REST, gateway and voice, and the page draws the room. Its unread count reaches the title bar tab and Exo's taskbar button through `friends.badge`. Exo no longer hosts, installs or patches the Discord desktop app.
- Every hosted app (Spotify, YouTube Music) is always optimized (`Helpers/AppOptimization.IsOn`). There is no setting; an older Exo's `appOptimizations` and `discordEquicord` keys in `settings.json` are ignored. The optimization is applied on every start of the app through Exo, so an app update that replaced its files is optimized again; an app running outside Exo is left alone. Spotify: `Helpers/SpotifyAmoledTheme` appends one marked block to the xpui stylesheet (black surfaces, and clutter hidden by `data-testid` and `href`), verified against a recorded stock backup; an xpui it does not recognize is left stock. It also writes two of Spotify's own prefs (`ui.hide_hpto`, `ui.hide_promoted_songs`) and adds a Canvas pause to the DevTools script `Helpers/SpotifyControls` registers. YouTube Music: `Helpers/EmbeddedClientPresentation` registers a document script that marks the page, and CSS scoped to that mark hides Premium upsells and stops painting a hidden room's video.
- Music hosts the selected provider (`music.*`). Spotify is a desktop app, hosted as an owned popup by `DesktopClientHost` (ownership, not SetParent: a reparented Chromium window loses activation and swallows keyboard input) — Spotify installed on consent (its signed installer), started hidden the first time the Music room opens, embedded into the room, hidden with it, closed with Exo. Changing the provider retires the previous session off the UI thread (`RetireAsync`: polite close, bounded wait, terminate) and the replacement host waits for that tree to be gone before launching, because the clients are single-instance. YouTube Music and Apple Music are their own web players (music.youtube.com, music.apple.com) on the embedded WebView2 profile (`MusicWebPolicy`). `Services/MediaSessionService` reads the provider's Windows media session (SMTC) for the mini player's title/artist/artwork/position and answers transport controls through it. The mini player's volume is the app's own, one control with the app's slider: `Services/MusicAppVolume` reads and writes it inside the page — Spotify's xpui over its loopback DevTools session (`Helpers/SpotifyPage`, the PlaybackAPI its own volume bar uses, found through the React tree), YouTube Music through Exo's WebView2 DevTools protocol (the player element), Apple Music the same way (the page's own `MusicKit.getInstance().volume`) — and long-polls it so a change made in the app reaches the shell as a `music.volume` event. The first time it answers while an audio session exists, the Windows session volume goes back to 100% with its level folded into the app's. A provider with no page to ask falls back to `Services/AppVolume`, its WASAPI per-session volume, which the mini player re-reads every second while shown. The mini player has no save-to-library action. Login belongs to the provider; there is no native MusicKit or Spotify SDK path (Apple Music uses the MusicKit JS that Apple's own page already runs).
- Music is Exo's own player for Spotify, YouTube Music and Apple Music (`ui/src/components/music/`: `NativeMusicRoom` runs the engine's lifecycle, `MusicPlayer` draws library, home, search, pages, panels and the player strip). Each service plugs in through an adapter in `ui/src/lib/musicAdapters.ts` that answers the same shapes (`ui/src/lib/player.ts`); the player shows Jam, Friend activity and Devices only for a service that has them. Spotify: `spotify.start` / `spotify.view` / `spotify.act` / `spotify.leave`, `MainWindow.SpotifyRoom`. The desktop app is started hidden through the same `DesktopClientHost` and is never placed on screen unless the user must install or sign in (the room then falls back to the hosted `MusicRoom`). While the room is open `SetEngineWanted` keeps the tree from the idle freeze; every call also wakes it and retries while the page thaws. `Helpers/SpotifyNative` installs one adapter in xpui over the loopback DevTools session (`SpotifyPage`): Spotify 1.3 keeps its platform APIs in a registry keyed by `Symbol.for(name)` (PlayerAPI, LibraryAPI, PlaylistAPI, ShowAPI, ConnectAPI, ConnectDevicesAPI, SocialConnectAPI for Jam, BuddyFeedAPI for Friend activity, RecentlyPlayedAPI, RequestBuilder…), found through the React tree; catalogue pages (home, search, album, artist) go through the client's own GraphQL request with this build's persisted-query hashes, which `Helpers/SpotifyQueries` reads from the installed xpui.spa by name and caches until the archive changes, and lyrics through the client's RequestBuilder to color-lyrics, as its own lyrics view does. Library filters and sort orders are LibraryAPI's own (ids and names); covers resolve `spotify:image:` and `spotify:mosaic:` URIs (a playlist without its own picture) at 300 px for rows and 640 px for headers. Answers are shaped in the page into small DTOs (cards, tracks, a header); the host only validates Spotify URIs and ids and forwards them. Spotify makes every request with its own session: Exo never reads a token, never plays or decodes audio, and changes nothing about what the account may do; a Jam's join token stays in the page and only its share link leaves it. YouTube Music: `ytmusic.start` / `ytmusic.view` / `ytmusic.act`, `MainWindow.WebMusicRoom`. The embedded music.youtube.com page loads in a background state (transparent, no input) and `Helpers/YouTubeMusicNative` evaluates in it through Exo's WebView2 DevTools protocol: pages from the page's own InnerTube client (`ytmusic-app` networkManager: /browse, /search, /next, /like), playing and skipping through its own `yt-navigate` event with watch endpoints, shuffle and repeat through its player bar, queue and like state from its own store. Ids cross as `ytm:<kind>:<id>`. Apple Music: `applemusic.start` / `applemusic.view` / `applemusic.act`, the same `MainWindow.WebMusicRoom` and web view. Its Windows app is native WinUI/C++ (AMP.*.dll) with nothing to drive without UI automation, so the engine is Apple's own web player instead: music.apple.com (opened on its light search page) runs hidden, and `Helpers/AppleMusicNative` evaluates in it through the page's own MusicKit instance (`MusicKit.getInstance()`): pages from `api.music` (the Apple Music API with the page's own developer token and the user's sign-in, which Exo never reads): `/v1/me/recommendations?name=listen-now` for Home (the editorial `music` grouping when signed out or empty), `/v1/me/recent/played`, catalog search, albums, playlists and artist views, the library's playlist folders, albums and artists, lyrics TTML; playing through `setQueue` / `playLater` / `changeToMediaAtIndex`, shuffle and repeat through `shuffleMode` / `repeatMode`, and favorites, library and playlist edits through the same `/v1/me/favorites`, `/v1/me/library` and playlist-tracks calls the page's own menus send. Play and transport are evaluated as the user's click (`userGesture`), which only follows a click in Exo. Playback and its DRM (PlayReady or Widevine in WebView2) stay inside Apple's page. Ids cross as `am:<type>:<id>` with the API's own types. While hidden its page is skipped by layout and paint (`EmbeddedClientPresentation`, `content-visibility`). The Apple Music Windows app is no longer hosted, installed or optimized: its host spec, winget install, caption cut-out and black-surface theme helper (`ExoLauncher.AppleMusicTheme`) are gone. Cider is no longer a music service; a saved Cider choice reads as Apple Music (`WebClientPreferences`, `savedMusicService`).
- Devices is Exo Mouse, a separate program in `mouse/` (AGPL-3.0-or-later, `mouse/LICENSE`) built on OpenMouse's protocol library `@openmouse/protocol` (AGPL-3.0, pinned 0.42.2). Exo Launcher is not covered by the AGPL; the two meet only through postMessage. The module's source is public at github.com/ImAvgErix/exo-mouse and must be pushed there for each release that ships a changed module. The `ui` build runs `npm --prefix ../mouse run build` into `ExoLauncher/wwwroot/mouse`, and `DevicesRoom.tsx` shows it in an iframe on its own origin, `https://mouse.exo-launcher.local` (`.exo-devices-frame`), filling the room. The page relays only `hid.list`, `hid.open`, `hid.close`, `hid.sendReport`, `hid.sendFeatureReport`, `hid.receiveFeatureReport` and `hid.receiveInputReport`, plus `exo.games` (installed games by id, title and Exo's own cached cover thumbnail, for linking mouse profiles to games) and `exo.profiles.read`/`exo.profiles.write` (its saved profiles, `mouse.profiles.get`/`set`, kept in `mouse\profiles.json` under Exo's data folder, at most 512 KB), and takes one-way notices and battery state from it (shown as Exo status lines and the title-bar battery chip), plus `exo.textScale` and `exo.motion` (Exo's text size and reduce-motion setting, so the module's type and motion follow Exo's), and passes back only `hid.input`, `hid.changed`, `game.runState` (id and running), `room.visible`, `exo.textScale` and `exo.motion`; messages from anywhere but that frame, and every other method, are ignored. The relay is installed once and never removed, so the module keeps working while the room is hidden. Native HID is `Services/Hid/HidService` (+ `HidInterop`) behind `WebHostBridge.Hid`: it lists devices the way WebHID does (collections grouped by their parent USB interface, so two identical mice stay separate), opens every collection shared, never exclusive (which would freeze the mouse's own input), of the collections Windows keeps for itself skips keyboards and opens a mouse or pointer collection with no access, for its feature reports only, reads input reports from the moment a device opens, matches Chromium's byte conventions, gives up on a blocked control transfer after 3 s, and announces arrivals and removals through `CM_Register_Notification`. Devices are named by an opaque hashed key; no device path reaches the page. No vendor software, bridge or driver install. `mouse/scripts/patch-protocol.mjs` runs before each build: the library's decoder ignored commands 16 and 17, which the Finalmouse Starlight X receiver uses for DPI and polling rate, so it could not read a Starlight X at all, and its driver refused the receiver light's TMR-DS mode (4) and never read the custom color (command 54), both of which Finalmouse's xpanel uses; the script fixes those and stops the build if the library version changes. Exo serves no OpenMouse Bridge API on 127.0.0.1:17846: the earlier web panel and Exo's own bridge are gone. `Services/MouseBridgeRetirement` runs once after that: if Use Exo's bridge had stopped the OpenMouse Bridge app (`settings.json` `mouseBridge: "exo"`), Exo's `openmouse-bridge.json` profiles are written into the app's `config.json` (never while it runs), then the settings are cleared. The app's sign-in entry is not put back (two programs driving one mouse conflict), and the app is not started.
- Store (`Services/StoreService*.cs`, `store.*`) reads only public, anonymous storefront endpoints and caches each answer under `store`. Home: Steam's IStoreQueryService/Query (top sellers, coming soon, and on sale with `price_filters.min_discount_percent`), the most-wishlisted search list and Epic's free games, saved as `home-v5.json`. Card facts (art paths, review summary, release, regional price text, tag ids) come from IStoreBrowseService/GetItems in batches of 50 and persist in `items-v2.json` (fresh 12 hours, kept two weeks); tag names from IStoreService/GetTagList persist a week in `tags-v1.json`. `store.game` answers from appdetails (4 s, then one 8 s retry) plus GetItems (3 s cap), deduplicates concurrent asks (hover warm-up, then click) and caches 20 minutes; `store.gameOffers` adds CheapShark's official-store rows (3 s). Epic's own GraphQL is not used: it sits behind Cloudflare bot protection, which refuses non-browser clients, and Exo does not work around that. A game's PC requirements are read out of Steam's HTML in its many shapes (`StoreService.Specs.cs`) and judged against this PC at answer time (`StoreService.Fit.cs`, `Helpers/SystemSpecs.cs`: processor, graphics card, installed memory and Windows read once, free space on the roomiest Steam library drive read each time); cards and processors sit on one rough performance scale per kind and are compared with the same maker's part when the game names one. Search caches 5 minutes per query and a newer query cancels the one in flight. `store.changed` carries `what` (`home` or `wishlist`) so the room reloads only that part. PERF lines in app.log time each source.
- Covers: `Services/CoverArtService` caches art under `covers\`, which the shell reads through the `covers.exo-launcher.local` virtual-host mapping (no UI-thread work). Grid cards and the transfer queue instead ask `thumbs.exo-launcher.local/<cover file>?w=<px>` (`ui/src/lib/coverThumb.ts`): `MainWindow.ThumbnailResourceRequested` defers the request to `CoverArtService.ReadThumbnailAsync`, which scales that exact JPEG with Windows.Graphics.Imaging (Fant, EXIF-oriented, sRGB) so the card covers its box, stores `thumb-<w>-<stamp>-<cover>.jpg` beside it (stamp = hash of the source's length and write time, so a replaced or custom cover gets a new thumbnail and the old one is deleted), and serves the original when it is PNG/GIF/WebP or already within ~15% of the size. `w` is the widest card the screen can produce at any window size times the device pixel ratio, rounded up to 120 px (240 at 1080p and 1440p at 100%, 360 at 4K); it only grows within a session, and above 720 cards take the original. The game sheet's cover always loads the full file and shows the card's bitmap until it decodes. Thumbnails are ordinary cover-cache files for maintenance and eviction.
- Achievements are read natively per store (`Services/AchievementService`) once after a launched game exits. Steam reads `librarycache/achievement_progress.json` (counts for every game) first, then the per-game librarycache file, then the Web API when a key is stored. The counts stay on this PC. There are no unlock pop-ups and React does not query them.
- Shaders: System > Shaders is Exo Shaders, Exo's own shader add-on (a GPL fork of SCSKiller 1.3.0, source at github.com/ImAvgErix/exo-shaders): a headless engine service (`Services/ShadersAddon`, NDJSON over stdio) and its page, framed in the GPU sheet's Shaders tab through `shaders.addon` / `shaders.call` (`MainWindow.Shaders`). Exo hosts no shader app's window; without the add-on the tab says Exo Shaders is not installed. `Services/ScsKillerStatus` answers `shaders.estimates` (each game's compile time on this PC, for the queue's time) and `shaders.status` for a game sheet from the engine's `games.json` (written when it scans) and each game's `games\<id>\state.json` (written when a compile ends; Warmed only for a `WarmedDriverId` whose driver version is installed now), watches both to post `shaders.changed`, and once deletes the \`tools\scskiller` copy older Exo versions downloaded.
- Upscalers: `Services/DlssSwapService` finds DLSS / FSR 3.1 / XeSS files in a game, swaps them with backups (`.exo-orig`, written-hash and stale markers) and restores them byte for byte. Releases are the compiled-in pins (SHA-256), each vendor's newer GitHub releases (`DlssSwapService.VendorWatch`: as Exo opens, at most hourly, NVIDIA DLSS, AMD's FSR SDK and Intel XeSS are asked for their latest release; a newer one's DLLs that a scanned game ships are fetched from its commit, checked against GitHub's size and git blob hash and the vendor's signature, and kept in `dlss\vendor-releases.json` with their SHA-256) plus DLSS Swapper's public manifest (`DlssSwapService.Catalog`, fetched at most daily into `dlss\catalog-v2.json`; dev, unsigned and DLSS 1 builds dropped). FSR 3.1 builds are compared by the release they are known by (1.0.2.38022 is 3.1.2), not their loader's version. A catalog file is used only after its first download matches the manifest's size and MD5 and passes the vendor signature, export and exact-version checks; its SHA-256 then goes into `catalog-trusted.json` and every later use is checked against it like a pin. Downloads come only from the pinned GitHub URLs and `dlss-swapper-downloads.beeradmoore.com/<kind>/`. DLSS's three files and FSR 3.1's two share one release id, so an update sets its siblings to the same release. Exo only ever moves a file to the newest release (the UI offers no older one).json` whose Exo-written file is older than the newest or was replaced by a game update or store verify, skipping running or updating games and going through the same consent and apply path. DLSS presets are part of the GPU profile below. NVIDIA's NGX overlay (`NGXCore\ShowDlssIndicator`, HKLM) is changed only through an elevated `reg.exe`, so Windows prompts each time.
- Capture: Exo Capture (`capture/`, C++, GPL-3.0-or-later, `capture\build.ps1`) is a separate program, shipped under `addons\capture` (or `%LOCALAPPDATA%\ExoLauncher\addons\capture`, which wins), started with the connected rooms by `Services/CaptureAddon` and spoken to in NDJSON over its stdin/stdout (`MainWindow.Capture`, `capture.*`, events `capture.state` / `capture.saved`). It captures the running game's window (found by its process image under the game's install folder; `game` from Exo's run state) or the screen with Windows.Graphics.Capture (frames no faster than the clip's rate, 60 or up to 120 fps; the converter reads the capture surfaces directly; Exo Capture's GPU work runs at the lowest priority). When Windows capture gets no frame from a game window for five seconds (exclusive full screen), it takes the frames from inside the game with OBS Studio's own signed graphics hook (`capture\third_party\obs`, OBS's anti-cheat compatible injection through a message hook on the game's window thread; `src/hook.cpp` speaks OBS's hook protocol: keepalive mutex, hook info map, shared texture). Never for Riot games, while FACEIT or ESEA runs, for Store apps, or when another app (OBS) already captures that game. It converts on the GPU (D3D11 video processor, BGRA to NV12/P010) and encodes with the GPU's Media Foundation encoder (NVENC, AMF, Quick Sync on the capturing GPU's own adapter; AV1, else HEVC, else H.264, only a codec Windows can play back, stepping down a codec when a listed encoder refuses to start), so frames never touch the CPU. Sound is always four AAC tracks: the mix on track 1, then the game (WASAPI process loopback of its process tree; on the desktop everything except Discord), Discord's tree (looked for again while it is not running or after it restarts) and the default microphone; a missing source is a silent track. Instant replay keeps encoded packets in RAM from a key frame (one a second); Save writes them to MP4. A recording writes MP4 plus a packet journal (`.exo-rec`) that rebuilds the file if it was cut short (Windows' fragmented MP4 writer takes H.264 only). Trim is a key-frame cut without re-encoding; Discord and Vertical exports re-encode to H.264. Snips are taken by the add-on (frozen screen, drag, click a window, Enter for the screen), copied at once, saved as PNG and opened in the Captures sheet's snip editor (the host brings Exo forward on `capture.saved` with kind `snip`); on an HDR screen the frozen picture comes from desktop duplication in FP16 scRGB, tone-mapped to sRGB against Windows' SDR white level. Its toast is its own topmost window. The shell reads the captures folder and thumbnails from `captures.exo-launcher.local` and `capture-thumbs.exo-launcher.local`. Without the add-on the Capture button and Settings rows do not show.
- Exo has no account or server of its own. `Services/LegacyProfileDataCleanup` runs once per start (deferred, after the shell paints) and deletes, by exact name in `%LOCALAPPDATA%\ExoLauncher` and `%APPDATA%\ExoLauncher`, what retired features left behind; for the retired Exo account that is `auth.bin` (+ `.tmp`) and `online-cache`. It never contacts a service.
- GPU profile (`Services/GpuProfileService`, `gpu.profile` / `gpu.import`, System > Graphics > Driver and profile): one NVIDIA global profile per GeForce series (GTX 10/16, RTX 20/30/40/50) in two variants the user picks, G-SYNC or No G-SYNC (preselected from the main screen's variable refresh as the driver reports it, `Helpers/NvidiaProfiles.Vrr`). `Helpers/GpuProfile` holds every value (pure, tested); `docs/architecture/gpu-profiles.md` has each setting's verdict, reason and source, built from a real global profile and NVIDIA's NvApiDriverSettings.h. G-SYNC: on for full screen and windowed, driver V-Sync on, NVIDIA Reflex's cap (refresh x 3600 / (refresh + 3600)); No G-SYNC: variable refresh off, V-Sync and caps the games'. Both: Low latency On, a shader cache that never shrinks, DLSS presets per series (RTX 20/30 SR K and RR D; RTX 40/50 NVIDIA's recommended SR, RR and FG), and NVIDIA's defaults back for placebo or harmful tweaks. Use Exo's profile writes every setting of the variant that the driver lists (EnumAvailableSettingIds) to the global profile in one session and save, after saving every value it replaces to `gpu-profile.json` (with the variant); Undo writes those back (null restores NVIDIA's predefined value) and a re-apply or variant switch keeps the first backup. Each read compares the driver with the applied variant, so a driver update or another tool that moved a value shows with Re-apply. The page shows no individual settings. A Profile Inspector .nip (`Helpers/NvidiaProfileImport`) of the global profile (one that names no program) is read into a plain-words preview and applied to the global profile; Undo puts back what it replaced (kept in memory until Exo closes). AMD (`Helpers/AmdAdlx`) and Intel (`Helpers/IntelIgcl`) get what to set by hand, next to what their driver holds; Exo writes neither.
- Settings is one page: General, Downloads, Music and Discord, Capture, Game stores, Optional keys, About.

The only native XAML is `MainWindow`. `ExoLauncher/Ui/` holds small host helpers (format, cover fill, URL launch, drag regions), not a second room system. Do not rebuild native rooms when changing the React UI.

`hostMock.ts` loads only during development/test. Protocol v1 method names and update-result types are checked against native source by `npm run contracts`; intentional changes regenerate `ui/contracts/host-v1.json` and `hostWire.ts` with `npm run contracts:write`. `npm run dead` runs knip in both default and production mode (`knip.production.json`), so a file or export reachable only from tests fails the gate. `npm run css:prune` reports stylesheet blocks whose classes no component uses. `tools/find-dead-types.ps1` lists host types with no references outside their declaration. Cache lifetime and recovery ownership are documented in [docs/CACHE_POLICY.md](docs/CACHE_POLICY.md).

`npm run build` in `ui` emits assets into `ExoLauncher/wwwroot`. The project build invokes it before collecting web assets. The shipped app runs from `%LOCALAPPDATA%/ExoLauncher/app`. Validate both the frontend and installed WebView2 after deployment.
